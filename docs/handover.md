# 인수인계

## 1. 마이그레이션 배경과 이유 (왜 이렇게 했는가)

### 1.1 Cloud Run 운영 리전 통일 (`us-central1` → `asia-northeast3`)

- **배경**: 백엔드 Cloud Run(`aim-be-prod`)은 `us-central1`에 있었으나, Firestore와 Artifact Registry는 이미 `asia-northeast3`에 위치했습니다. 이 리전 불일치로 인해 레이턴시 지연, 네트워크 비용 증가, 운영 혼선이 발생했습니다.
- **조치**: 백엔드 배포 workflow의 `CLOUD_RUN_REGION`, 배포 검증 스크립트의 리전 가드, Terraform 변수(`region`/`cloud_run_region`) 기본값, 그리고 프론트엔드의 `firebase.json` `/api` rewrite 리전을 모두 `asia-northeast3`로 통일했습니다.
- **컷오버 주의사항**: Cloud Run v2는 location이 immutable이므로 신규 서비스가 새 리전에 생성됩니다. 따라서 반드시 **(1) 백엔드를 `asia-northeast3`에 먼저 배포 및 헬스체크** 한 뒤, **(2) 프론트엔드의 `firebase.json` rewrite를 전환 (프론트 main 머지 = 프로덕션 자동배포 = 즉시 컷오버)** 하는 순서를 지켜야 합니다. 역순으로 진행하면 `/api`가 존재하지 않는 리전으로 라우팅되어 전면 장애가 발생합니다.

### 1.2 프론트 렌더링/배포 구조 (정적 export + `/api` rewrite)

- 앱 기준은 Next.js App Router입니다. 배포는 `out/` 정적 산출물 기반으로 Firebase Hosting을 이용합니다. 공개 페이지는 SSG, 로그인 이후 내부 페이지는 CSR이 기본 전략입니다. (자세한 근거는 [페이지 렌더링 전략](page-rendering-strategy.md) 참고)
- `/api/**` 경로의 요청은 Firebase Hosting의 rewrite 설정을 통해 백엔드 Cloud Run(`aim-be-prod`)으로 프록시됩니다. 이를 통해 프론트엔드는 정적으로 배포되면서도 동적인 API를 함께 사용할 수 있습니다.
- `main` 브랜치 머지는 곧 프로덕션 자동 배포(Firebase Hosting live)를 의미합니다. 이러한 자동배포 성질 때문에 리전이나 도메인 변경처럼 되돌리기 어려운 변경 작업은 반드시 앞서 언급한 배포 순서를 엄수해야 합니다.

### 1.3 크롤링 데이터 파이프라인의 진화

- **초기**: 소프트콘 크롤러(Python, 별도 repo)가 크롤링 결과를 백엔드의 `posts` 테이블에 직접 적재하는 구조였습니다.
- **현재**: 백엔드에 크롤링 전용 도메인 및 API(`/api/crawled-projects`, 엔티티: `CrawledProject`, `Member`)가 분리되었습니다. 크롤러가 이 API를 통해 데이터를 적재하며, 학생 유저는 자신이 참여한 프로젝트(가입 이름/이메일과 크롤링 이름/이메일 대조)를 개인 페이지에서 확인하고 원클릭으로 포트폴리오(`Post`)로 가져올 수 있습니다.
- **남은 논의 (백엔드 이슈 트래킹)**: 포트폴리오 가져오기 시 중복 생성 방지(멱등성) 및 가져온 포트폴리오의 visibility 강제. 전체 목록 및 페이지네이션 처리는 별도 페이지와 API가 담당할 예정입니다.

## 2. 코드 리뷰 기준 (이 팀의 리뷰 원칙)

실제 PR 리뷰(#184 로딩 UI 통일, #179 공지 페이지 스펙) 및 CI/CD PR에서 적용한 팀 내 리뷰 기준입니다.

- **우선순위**: 실질적인 버그(런타임 오작동)를 최우선으로 확인합니다. 스타일이나 개인 취향 차이는 비블로킹(Non-blocking)으로 취급합니다.
- **접근성은 하드룰**: 로딩 및 상태 표시 UI에는 `role=status`, `aria-live`, `sr-only` 등의 접근성 속성이 올바르게 유지되는지 반드시 확인합니다.
- **레이어 및 네이밍 컨벤션 준수**: `camelCase`/`PascalCase`, `is`/`has` 불린 접두사를 정확히 사용해야 합니다. `import` alias 계층 규칙(`src/app`=라우팅, `src/screens`=화면, `src/api`=데이터)을 철저히 지킵니다.
- **재사용 우선 (과설계 금지)**: 새로운 컴포넌트를 만들기 전에 기존 공용 컴포넌트와 유틸리티를 먼저 찾아서 재사용합니다. 최소한의 코드로 문제를 해결하는 것을 지향합니다.
- **전역 컴포넌트 변경은 영향 범위를 문서화**: 공용 Button 등 전역에 영향을 미치는 변경사항은 영향을 받는 사용처를 PR 본문에 표로 정리하고 확인해야 합니다.
- **비블로킹 개선점 분리**: 리뷰 중 발견한 당장 수정하지 않아도 되는 리팩터링이나 버그는 별도의 follow-up 이슈로 분리하여 관리합니다.
- **교차검증**: 큰 변경사항(마이그레이션 diff 등)은 서브에이전트나 봇(CodeRabbit)의 리뷰로 한 번 더 걸러냅니다. 봇의 지적사항은 현재 코드 기준으로 검증하여 유효한 것만 반영하고, 나머지는 명확한 근거와 함께 리젝(Reject)합니다.
- **이슈 및 PR 컨벤션**: PR 제목은 백엔드의 경우 `[Feat]/[Fix]/[Chore] 설명`, 프론트의 경우 `[Feat]/[Fix] #이슈번호 - 설명` 형식을 따릅니다. 라벨은 `bug`, `enhancement` 등 기존 라벨을 일관되게 사용합니다. 머지는 리뷰어가 수행합니다.

이 문서는 살아있는 문서다 — 관례가 바뀌면 갱신한다.
